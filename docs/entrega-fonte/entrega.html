O que é

Sistema web para agendar a entrega de caminhões no recebimento do CD, com controle de capacidade de paletes por dia (480) e por faixa horária (120 em 4 faixas de 2 h). Não paletizado conta em dobro. A capacidade excedida gera alerta, sem bloquear. Ao agendar, o fornecedor recebe e-mail de confirmação. Há relatório por período com CSV, perfis com permissões validadas no backend e auditoria de todas as ações.

Como rodar localmente

Pré-requisito: Docker Desktop (ou Docker com o plugin Compose). Não é preciso instalar Java, Node nem PostgreSQL.

git clone https://github.com/JP-Legend/desafio-krill-agendamento.git
cd desafio-krill-agendamento
docker compose up -d --build
docker compose ps        # aguardar os 4 serviços como "healthy"

Stack

BackendJava 17+, Spring Boot 3.5 (Web, Validation, Data JPA, Security com JWT), Flyway (V1 a V16), springdoc/Swagger, SMTP, Web Push
FrontendVue 3, Vite, PrimeVue, PWA
BancoPostgreSQL 16
InfraDockerfiles multi-stage sem root, nginx, docker-compose com db, api, web e Mailpit
TestesJUnit 5, Mockito, Testcontainers (Postgres real), JaCoCo; Vitest e Vue Test Utils

Banco de dados: por que PostgreSQL

  • Integridade: agendamento, faixa, caminhão, paletização, CD, loja, fornecedor e auditoria são relacionais. As migrações Flyway criam chaves estrangeiras, UNIQUE e CHECK no próprio banco.
  • Agendamentos simultâneos: cada agendamento roda numa transação que pega pg_advisory_xact_lock por data. Dois usuários no mesmo dia são atendidos em fila e a soma de paletes do alerta não fica errada.
  • Ocupação: o agendamento guarda os paletes equivalentes; a % do dia e de cada faixa é calculada no domínio (CalculadoraOcupacao) a partir de uma consulta indexada por data.
  • JSONB no “antes/depois” da auditoria e índices parciais nos tokens públicos.
  • Flyway versiona o esquema; open source; roda na imagem oficial no compose e nos testes via Testcontainers (sem H2).

Decisões de arquitetura

  • Clean Architecture: domain (regras puras, sem Spring) → application (casos de uso e portas) → infrastructure (JPA/JDBC, SMTP, push, JWT, BCrypt, ERP) e web (REST). Os casos de uso são montados em UseCaseConfig e testados com Mockito sem subir o Spring.
  • Frontend e backend separados, conversando só por REST/JSON em /api/v1 com JWT. Permissões decididas no backend.
  • Alerta em vez de bloqueio: a calculadora devolve os alertas; o caso de uso salva e repassa para tela, e-mail e push.
  • Mailpit como SMTP de desenvolvimento: os e-mails ficam visíveis em localhost:8025 e nada sai para fora. Envio assíncrono.
  • Docker multi-stage: imagens finais só com JRE Alpine e nginx sem root, camadas do Spring Boot separadas para cache.
